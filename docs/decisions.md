## 2026-04-24: 项目命名

**决策**：项目命名为 `zoob-verse`

**理由**：
- `graph` — 体现核心技术（知识图谱、图分析）
- `lore` — 指"传说、知识、特定领域的知识体系"，涵盖文学、影视、游戏等
- 不局限于"文学"，唐诗、美剧、游戏世界观都能装进来
- 简洁、好记、有辨识度

**备选**：`literary-research`（太宽泛、偏学术）、`world-graph`（可能误解为地理）

- 核心对象保持稳定，扩展维度按语料配置。

## 2026-05-01: LightRAG 模型对比结论（越女剑实测）

**决策**：默认模型定为 gpt-4o，追求极致质量时不考虑 token 可用 o3-mini

**实测数据**：
| 模型 | 实体 | 关系 | 孤岛率 | 评价 |
|------|------|------|--------|------|
| gpt-4o | 153 | 254 | 0.0% | 零孤岛，折中首选 |
| o3-mini | 173 | 264 | 6.9% | 不计 token 效果最好 |
| mimo-v2.5-pro | 502 | 867 | 3.8% | 提取激进但 token 消耗夸张 |
| gpt-4o-mini | 109 | 138 | 8.3% | 快速低成本 |
| gemini-2.5-pro | 249 | 474 | 17.7% | 信息密度好但孤岛率高 |

**理由**：
- gpt-4o 零孤岛率，质量最稳定
- mimo-v2.5-pro 虽提取量大但消耗的 token/时间/成本不合理
- o3-mini 质量高但孤岛率也更高，适合不计成本的场景

## 2026-05-01: Prompt 版本分工

**决策**：
- V7（严格纯文本）：主力 Prompt，适用 gpt-4o、o3-mini、gemini-2.5-pro
- V8（V7 + Few-Shot）：仅 gpt-4o-mini 等小模型
- V3（JSON）：mimo-v2.5-pro 专用（纯文本会导致 IndexError）
- V6（纯文本）：gemini-2.5-pro 专用（历史遗留）

**理由**：
- V7 的 <|#|> 分隔符 + <|COMPLETE|> 结尾对国产模型和 OpenAI 模型都稳定
- V8 的 Few-Shot 示例对非推理模型是额外 token 负担，仅小模型需要
- MiMo 对 JSON 格式兼容更好，纯文本反而触发解析错误

## 2026-05-01: 推理模型（o 系列）不适用于实体提取

**决策**：禁用 o1-mini、o4-mini 等推理模型用于 LightRAG 提取阶段

**理由**：
- 实体提取是格式化任务，不需要推理链
- 每轮 API 内部生成隐藏推理 token，耗时 30-90s，消耗是普通模型的 3-5 倍
- o1-mini：112s/小chunk，Cloudflare 524 超时
- o4-mini：11分钟卡在 9/15 chunk，推理链过重
- 推理模型留给需要逻辑推导的 query 环节

**注意**：o3-mini 表现不同——之前成功完成提取（173实体/264关系/6.9%孤岛率）
说明 o 系列内部也有差异，不能一概而论，但 o4-mini 确认不可用。

## 2026-05-01: gpt-5-mini 不可用于 XiaoAI + LightRAG

**决策**：不推荐在 XiaoAI 代理下使用 gpt-5-mini 做批处理提取

**理由**：
- 单个 3 句 chunk 耗时 112s，远超 gpt-4o-mini 的 3-5s
- Cloudflare 代理超时 120s，大量 chunk 触发 524 错误
- 虽 Token 价格低，但实际耗时过长，有效成本反而更高
- 即使禁用 chain-of-thought 仍保留底层推理负载

## 2026-05-06: GraphRAG 查询机制与 debug-query 需求

**决策**：将 GraphRAG / LightRAG 明确定位为“证据召回与组织层”，不是图数据库自动推理引擎；查询阶段仍然依赖 LLM 的综合能力。

**理由**：
- 图谱的核心价值是把长文本压成可复用的实体、关系、路径和证据，而不是取代查询模型。
- 查询答案的质量仍受 LLM 智力、上下文选择、问题表述和证据整合能力影响。
- 对文学分析尤其重要的，不只是最终答案，还要能审计“召回了什么证据、为什么召回、答案如何形成”。

**后续动作**：
- 增加 `debug-query` 模式，至少保存召回实体、关系、chunks、query prompt、final answer。
- 在模型对比阶段优先看可审计链路，而不是只看答案文本是否好看。

**结论**：
- GraphRAG / LightRAG 适合扩大有效上下文和沉淀结构化证据，但不是替代查询阶段 LLM 智力。

## 2026-05-07: 分层辅助输出的定位

**决策**：`events.json`、`facets.json`、`views/` 定位为从 `graph.normalized.json` 派生的实验性辅助层，不作为主图谱本体，也不视为最终文学分析结论。

**理由**：
- 主图谱应保持单纯，避免把尚未稳定的研究维度硬塞进实体类型或关系类型。
- 事件候选、研究标签和主题材料页适合帮助研究者浏览材料，但第一版主要是规则整理，不能等同于深度洞察。
- 这些派生层不调用模型、成本低，适合快速试错；后续若引入 LLM 丰富，应显式记录成本和模型。

**约定**：
- `graph.normalized.json` 是查询、评估和后续派生的基准图谱。
- `events.json` 是事件候选，不保证等于完整剧情事件表。
- `facets.json` 是标签索引，不代表实体只有这些含义。
- `views/*.md` 是主题材料页，供人工或 AI agent 继续分析，不作为最终稿。

## 2026-05-08: 孤岛优化策略

**决策**：孤岛优化先回到抽取质量与轻量 schema/prompt 设计，不优先做重型 normalize/audit/repair 流程。

**理由**：
- 孤岛通常来自三类原因：模型漏抽关系、关系格式错误被解析器丢弃、schema/prompt 对弱叙事关系不够友好。
- 孤岛不一定代表实体无价值。`湘妃`、`花园`、典故、地点、物件等辅助实体可能对文学分析有意义，问题是它们需要被合理挂回人物、事件或主题。
- 但“降低孤岛率”不能作为唯一目标。GPT-5.1 实验把孤岛率降到 1.48%，同时也带来更多泛关系和高密度连接，说明过度连边会削弱关系解释力。

**执行原则**：
- 不直接大幅放宽 schema，也不把所有孤岛都事后强行 repair。
- 先分析孤岛类型与来源，再选择少量稳定弱关系做小样本验证。
- 可候选的弱关系包括：`提及`、`发生于`、`相处于`、`象征`、`隐喻`、`参与`。
- 弱关系必须有文本依据，不能只为降低孤岛率而建立泛泛连接。
- 完整重跑前先用少量 chunk 比较孤岛率、泛关系率、关系退化率和查询质量。

## 2026-05-08: 当前默认路线与实验产物收敛

**决策**：后续默认采用“稳定 index + 分级 query + 高级模型基准验证”的路线。

**当前约定**：
- 默认 index 候选优先使用 `deepseek-v4-flash-zh-strict-bge-m3`，`doubao-seed-1.6-bge-m3` 作为同级对照。
- `gpt-5.1-bge-m3` 仅作为高召回/高质量基准和局部补强模型，不作为日常默认 index。
- 默认 query 先走小预算 profile：`top_k=6`、`chunk_top_k=4`、`max_total_tokens=10000`。
- `rerank` 保留为可选，不默认开启。
- 后续长篇试验优先选择《鸳鸯刀》作为下一部验证对象。

**产物收敛原则**：
- `runs/` 只保留代表性结果、关键对比和预算实验。
- 过渡 run、失败 run、重复 run 在结论已写入 `comparison.md` / `analysis.md` 后可以清理。
- 这样能降低后续 AI agent 读目录时的噪声，也避免同一结论被多个近似产物重复占位。

**更新（2026-05-08，《鸳鸯刀》实测）**：
- 《鸳鸯刀》32 chunks 完整索引后，`top_k=12` 查询容易召回过多关系，把上下文预算耗在图结构上，部分开放题没有正文 chunk。
- `top_k=6` 在同样 `chunk_top_k=4`、`max_total_tokens=10000` 下更平衡，查询总 tokens 从 `62132` 降到 `54037`，且开放题回答从失败变为可用。
- 后续默认小预算查询采用 `top_k=6`；只有在需要更高关系召回时再临时升到 `top_k=12`。
- 查询集问题必须显式限定作品名，避免泛问题抽到其他作品关键词。

## 2026-05-08: 《鸳鸯刀》DeepSeek vs Doubao index 对照

**决策**：保留 `doubao-seed-1.6-bge-m3` 作为同级 index 候选，但暂不替换 `deepseek-v4-flash-zh-strict-bge-m3` 为默认 index。

**实测结论**：
- Doubao index 用时 `1425.963s`，DeepSeek index 用时 `2255.488s`，Doubao 快约 `36.8%`。
- Doubao index LLM tokens `100934`，DeepSeek 为 `171022`，Doubao 少约 `41%`。
- Doubao 图谱更瘦：`185 nodes / 235 edges`；DeepSeek 为 `207 nodes / 284 edges`。
- DeepSeek 孤岛率更低：`14.98%` vs `17.30%`。
- DeepSeek 英文实体类型为 `0.00%`；Doubao 为 `1.62%`。
- Doubao 关系召回更收敛，查询时更容易保住正文 chunk；DeepSeek 回答整体更丰满。

**当前路线**：
- 默认 index 继续用 `deepseek-v4-flash-zh-strict-bge-m3`。
- 长篇效率压力较大时，用 `doubao-seed-1.6-bge-m3` 做优先对照或快速建图。
- 默认 query 固定用 `doubao-seed-1.6-bge-m3`，以减少 index 对比时的变量。

**记录**：
- 对比报告：`runs/jinyong/鸳鸯刀/comparisons/deepseek-flash-vs-doubao16-20260508/analysis.md`

## 2026-05-08: 跨作品主题视图原型

**决策**：先用多个单作品 `graph.normalized.json` 做本地跨作品视图，不急于建设全局图数据库或全局实体合并系统。

**理由**：
- 当前项目需要先验证“金庸宇宙”类问题是否真的受益于图谱，而不是过早增加复杂度。
- 单作品图谱仍是主数据源；跨作品层只负责按主题聚合和保留来源，便于审计。
- 本地 `cross-view` 不调用模型，成本低，适合快速验证女性角色、兵器宝物、核心价值等主题是否能形成可读材料。

**已实现原型**：
- CLI：`python -m src jinyong cross-view`
- 输入：多个 `--run-dir`、一个 `--topic`、一个 `--output-dir`
- 输出：`cross_corpus.json` 和 `<topic>.md`
- 试验输出：`runs/jinyong/cross/yuenvjian-yuanyangdao-20260508/`

**当前观察**：
- 《越女剑》+《鸳鸯刀》的跨作品 bundle 共聚合 `313` 个实体、`429` 条关系。
- 已生成 `女性角色`、`兵器宝物`、`核心价值` 三个视图。
- 主题视图能帮助快速看到跨作品材料，但第一版仍是规则筛选，不等于最终文学分析。

**限制**：
- 暂不做跨作品实体消歧；同名或泛名实体依赖 `corpus` 字段区分。
- 主题筛选主要依赖实体类型和关键词，仍需要人工复核。
- 只有当这些视图能稳定支持具体研究问题时，才考虑更重的全局 schema、向量检索或图数据库。

## 2026-05-09: 远端 worker 承载长任务

**决策**：中长篇作品的完整 index 可以交给远端 worker `root@hk.zoob.work` 执行；本地或任意 AI agent 只负责同步代码、启动 `screen`、查询日志、拉回 `runs/` 结果和清理远端目录。

**理由**：
- 《连城诀》这类十几万字作品索引时间已经明显超过适合守着本地电脑等待的范围。
- LightRAG index 的核心成本在在线 LLM / embedding API，本地算力不是主要瓶颈，普通小服务器可以作为稳定执行环境。
- `screen` 能让任务在 SSH 断开、本地关机、聊天 session 结束后继续运行。
- 结果目录 `runs/jinyong/<corpus>/<model>/lightrag/<run>/` 可以像一个实验数据包一样复制回本地继续可视化、查询、评估和归档。

**当前约定**：
- 远端项目路径：`/root/code/zoob-verse`
- 启动脚本：`scripts/run_remote_index.sh`，默认执行 `index -> normalize-graph -> audit-graph -> visualize -> report`
- 远端只作为临时 worker；结果拉回本地后清理远端 `runs/` 与 `logs/`，避免磁盘占满。
- 短期用 `rsync` 同步当前工作区快照，因为项目仍频繁调整；流程稳定后再考虑 git tag / release 方式。
- `.env` 可以复制到用户自己的远端服务器，但任何 agent 不能打印密钥内容。

**边界**：
- 远端 worker 解决的是执行持续性，不解决模型限流、provider 报错、prompt 质量或 schema 质量问题。
- 查询评估和可视化可以在本地补做，避免远端保存过多中间结果。

## 2026-05-09: 长篇作品工作流优化

**决策**：长篇作品进入分析前增加轻量 `clean-text` 预处理；长篇图谱人工检查优先使用子图；长篇查询默认使用 `--query-profile longform` 采集检索证据并限制图结构预算。

**理由**：
- 《连城诀》首次完整索引后，全图约 `887` 个实体、`1239` 条关系，完整 `graph.html` 已经接近当前 pyvis 展示上限，打开慢且布局闪烁，不能再作为长篇质量判断的唯一入口。
- 长篇 raw 文本里常见下载站、网址、合集序言等噪声，应在 index 前清掉，避免把无关文本建进图谱。
- 长篇查询不能只看答案是否流畅；如果没有正文 chunk 证据，文学分析答案很容易变成“图结构摘要”而不是可审计研究结论。
- 预算控制不是简单截断最终答案，而是通过 `top_k`、`chunk_top_k`、`max_entity_tokens`、`max_relation_tokens`、`max_total_tokens` 控制召回上下文构成。

**当前实现**：
- CLI：`python -m src jinyong clean-text --input raw.txt --output cleaned.txt --report cleaning.report.json`
- CLI：`python -m src jinyong visualize --focus 狄云 --hops 1 --subgraph-output ... --disable-physics`
- CLI：`python -m src jinyong visualize --top-degree 80 --disable-physics`
- CLI：`python -m src jinyong eval --query-profile longform`
- `queries.json` 记录 `evidence_status`。`not_collected` 表示本次没有采集 debug 检索数据；`insufficient_text_evidence` 表示已采集但正文 chunk 数不足。

**边界**：
- `clean-text` 只删除确定性噪声，不负责语义改写或删正文。
- 子图是人工查看入口，不替代完整 `graph.normalized.json`。
- `longform` profile 是默认保守起点；如果某类问题召回不足，再按问题类型调整，不把复杂检索策略一次性做重。

**验证（《连城诀》既有 run）**：
- 全图：`887` 实体、`1239` 关系，完整 `graph.html` 约 `753KB`，人工浏览明显吃力。
- 子图：`水笙.h1` 为 `44` 节点 / `128` 边，适合人工查看；`狄云.h1` 为 `303` 节点 / `659` 边，仍偏大；`狄云.h1.limit80` 和 `top-degree-80` 都控制在 `80` 节点左右，更适合长篇浏览。
- `--query-profile longform` 跑 7 个固定问题后，每题均得到 `5` 个正文 chunks，`evidence_status.status=ok`，比旧查询中出现 0 chunk 的情况更适合做可审计分析。

## 2026-05-09: 金庸宇宙后处理与文学 NLP 价值路线

**决策**：继续构建金庸作品图谱，但目标从“把每本书生成完整可视化图”调整为“单书 index + 后处理规范层 + 证据化查询 + 跨作品验证”的可累积数据路线。

**理由**：
- 全文 index 能较好覆盖主要人物、地点、组织、物件、武功和核心关系，但不能假设没有漏抽。模型会因 chunk 边界、上下文压力、schema 约束和关系表达复杂度漏掉部分弱关系或隐性关系。
- 重复节点、别名、孤岛、低价值节点不必在 index 阶段一次解决。更合理的做法是保留单书原始图谱，再在后处理阶段建立规范实体层、别名层、裁剪层和跨作品聚合层。
- 已抽出的信息可以后处理合并、归一、裁剪和重打标签；未抽出的信息不能凭空修复，必要时应回到原文做局部补抽或 targeted extraction，而不是盲目全量重跑。
- 图谱底座可以覆盖传统文学 NLP 的很多任务，例如词频/关键词、人物共现、人物关系强弱、地点轨迹、组织关系、主题/意象聚合、中心性分析和跨作品检索，并能比纯统计方法提供更强的语义解释与证据链。
- 但事实型查询必须优先依赖 corpus evidence，避免模型凭金庸常识脑补。回答应尽量能追溯到图谱实体、关系或原文 chunk。

**后处理分层约定**：
- 原始单书图谱：保留 `graph.json` / `graph.normalized.json`，不破坏抽取现场。
- 单书规范图谱：处理别名、重复实体、低价值节点、关系类型归一和孤岛分类。
- 跨作品实体层：将同一实体在不同作品中的提及对齐，例如人物、门派、地点、武功、物件、典故。
- 主题/研究层：按问题派生视图，例如宝藏母题、师徒背叛、冤狱结构、女性角色命运、宗教/门派功能、空间移动路径。
- 证据索引层：保留每个结论关联的作品、chunk、实体和关系，面向可审计查询。

**文学 NLP / 图谱可验证任务**：
- 字典型检索：某人物、门派、武功、地点在哪些作品中出现或被提及。
- 人物网络：主角与谁关系最密、关系类型如何变化、哪些边缘人物间接推动主线。
- 空间分析：主角去过哪些地点，地点在叙事中的功能是什么。
- 母题分析：宝藏、秘籍、复仇、冤狱、隐居、师门背叛等结构如何跨作品复现。
- 角色功能分析：高人、恶父、伪君子、被误解者、牺牲者等叙事角色在不同作品中的变体。
- 传统 NLP 对照：词云、关键词、共现网络、情绪/主题变化可以作为 baseline，但不作为最终解释。

**阶段性路线**：
- 不直接一口气跑完所有长篇。
- 先新增 2-3 部代表性作品，形成可验证的小型金庸宇宙样本。
- 每新增一批作品后，必须回头检查：覆盖率是否足够、后处理是否能改善重复/孤岛、跨作品查询是否产生比普通全文问答更有价值的结果、成本是否还能接受。
- 如果跨作品查询只是把单书摘要拼接起来，应先优化跨作品实体对齐和证据检索，不继续盲目扩量。

## 2026-05-10: 跨作品主题视图的使用边界

**决策**：继续使用本地 `cross-view` 做跨作品预检，但只把它当作“已有实体和主题的聚合器”，不要把它误当成通用的语义联动引擎。

**理由**：
- 当前 `cross-view` 主要依赖主题关键词和少量预设规则，适合 `女性角色`、`兵器宝物`、`核心价值` 这类结构清晰的主题。
- 过于泛化的主题，例如 `人物联动`，如果没有预置映射或显式关键词集合，容易得到空结果。
- 这不是图谱本身无效，而是主题层筛选器仍然偏规则化；它更适合拿来验证“已有图谱能不能被重新组织成材料页”，而不是自动发现任意联动。

**当前观察**：
- 《雪山飞狐》与《飞狐外传》之间存在大量可复用共享实体，至少包括胡斐、胡一刀、胡夫人、苗人凤、金面佛、苗若兰、田归农、南兰、程灵素、袁紫衣、商老太、田青文、陶子安等。
- 这说明两部作品已经足够支撑跨作品人物、门派、武功、母题和空间的继续研究。
- 真正值得继续做的，不是空泛的“人物联动”标题，而是围绕具体共享实体和母题组织跨作品分析，例如胡斐/苗人凤/胡一刀家族线、田归农与南兰线、宝刀/宝藏/秘籍线、女性角色命运线。

**下一步约定**：
- 先做能稳定出结果的主题，如 `核心价值`、`兵器宝物`、`女性角色`。
- 再做手工指定的跨作品问题，而不是依赖泛主题自动匹配。
- 如果要更强的联动能力，后续应在 `cross-view` 之上加一个显式的主题词表或人工定义的联动层。

## 2026-05-10: 跨作品实体对齐先做后处理层

**决策**：跨作品实体对齐先作为独立后处理层设计，不直接改写单书 `graph.json` / `graph.normalized.json`，也不在当前阶段引入重型全局图数据库。

**理由**：
- 单书图谱是抽取现场，应保留原貌，便于追溯模型、prompt、chunk 和证据。
- 跨作品研究需要合并人物、地点、门派、武功、物件、家族、称号和母题，但这些合并有置信度和解释成本，不应硬写回原始图谱。
- 当前最重要的是继续积累代表性作品，同时保留一个明确的后处理路线，等图谱数量足够后再集中验证实体对齐是否能产生真正的跨作品价值。

**执行原则**：
- 优先对齐高价值实体，例如人物、门派/组织、地点、武功/秘籍、兵器/宝物、家族、称号。
- 母题和概念更适合放在主题/研究层，不一定作为实体本体强行合并。
- 对齐候选可由名称匹配、别名规则、描述相似、邻居相似和作品关系生成；最终应区分 `same_entity`、`related_entity` 和 `different_entity`。
- 只靠后处理能改善别名、重复、裁剪、关系归一和主题标签；如果重要信息在 index 阶段完全漏抽，应回到原文做局部补抽或 targeted extraction。

**研究备忘**：详见 `docs/research/2026-05-10-entity-alignment-roadmap.md`。

## 2026-05-10: 远端 worker 并行策略

**决策**：允许远端 worker 最多同时跑 2 路独立 index 任务，但只作为受控并行，不把 2G 级别远端机器当成无限队列。

**理由**：
- `run_remote_index.sh` 的输出目录由 `corpus/model/run_name` 决定，日志由 `log_dir` 决定；只要 screen 名、run name 和 log dir 不重复，多个进程不会互相覆盖。
- index 的本地 CPU 占用低，主要瓶颈在远端 LLM / embedding API 等待，适合有限并行。
- 但远端内存较小，双路 smoke test 时 available memory 已接近 100MB；继续增加路数或提高单进程内部并发不稳。
- DeepSeek 和 Doubao 可以分散 LLM provider 压力；OpenRouter 的 `baai/bge-m3` 已验证可返回 1024 维向量，可作为 BGE-M3 embedding 备选，减轻 SiliconFlow embedding 侧共享瓶颈。

**执行原则**：
- 并行任务必须使用独立 `screen` 名、`run_name` 和 `log_dir`。
- 优先组合不同 provider，例如 DeepSeek + SiliconFlow embedding 与 Doubao + OpenRouter embedding。
- 并行时保持 `llm_model_max_async=1`、`embedding_func_max_async=1`、`max_parallel_insert=1`。
- 长篇正式任务优先 1 路；只有 smoke test 稳定且远端资源充足时，才加第 2 路。
- 若日志停止推进、出现限流、available memory 长时间低于 100MB 或 swap 快速增长，应停止新增任务，必要时只保留一路。

**当前验证**：
- 新增模型 profile：`doubao-seed-1.6-openrouter-bge-m3`。
- OpenRouter `baai/bge-m3` embedding 单独调用成功，返回 1024 维向量。
- 远端双路 smoke test 已启动：`deepseek-v4-flash-zh-strict-bge-m3` 与 `doubao-seed-1.6-openrouter-bge-m3` 同时处理《越女剑》，两路均进入 chunk 抽取阶段。
