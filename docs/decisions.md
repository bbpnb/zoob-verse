# Decision Log

记录项目关键决策及其理由。

## 2026-04-24: 项目命名

**决策**：项目命名为 `zoob-verse`

**理由**：
- `graph` — 体现核心技术（知识图谱、图分析）
- `lore` — 指"传说、知识、特定领域的知识体系"，涵盖文学、影视、游戏等
- 不局限于"文学"，唐诗、美剧、游戏世界观都能装进来
- 简洁、好记、有辨识度

**备选**：`literary-research`（太宽泛、偏学术）、`world-graph`（可能误解为地理）

---

## 2026-04-24: 统一平台 vs 分散项目

**决策**：采用统一平台（Framework + Plugin），而非每个作品独立项目

**理由**：
- 核心代码复用（图引擎、CLI 框架）
- 单一依赖管理
- 跨作品分析天然支持
- Skill 与项目统一管理

---

## 2026-04-24: 模块独立 Schema

**决策**：各模块独立定义实体/关系类型，不共享统一 schema

**理由**：
- 不同作品的研究维度完全不同（武侠 vs 科幻 vs 诗歌）
- 提取逻辑、分析方法、输出形式都不同
- 不能假设一套接口处理所有内容

**更新（2026-05-07）**：
- 当前已转向“核心图谱 + 作品 profile + 分析标签层”的分层工作台。
- 不再追求每个模块一套完全隔离的死 schema。
- 核心对象保持稳定，扩展维度按语料配置。

## 2026-05-01: LightRAG 模型对比结论（越女剑实测）

**决策**：默认模型定为 gpt-4o，追求极致质量时不考虑 token 可用 o3-mini

**实测数据**：
| 模型 | 实体 | 关系 | 孤岛率 | 评价 |
|------|------|------|--------|------|
| gpt-4o | 153 | 254 | 0.0% | 零孤岛，折中首选 |
| o3-mini | 173 | 264 | 6.9% | 不计 token 效果最好 |
| mimo-v2.5-pro | 502 | 867 | 3.8% | 提取激进但 token 消耗夸张 |
| gpt-4o-mini | 109 | 138 | 8.3% | 快速低成本 |
| gemini-2.5-pro | 249 | 474 | 17.7% | 信息密度好但孤岛率高 |

**理由**：
- gpt-4o 零孤岛率，质量最稳定
- mimo-v2.5-pro 虽提取量大但消耗的 token/时间/成本不合理
- o3-mini 质量高但孤岛率也更高，适合不计成本的场景

## 2026-05-01: Prompt 版本分工

**决策**：
- V7（严格纯文本）：主力 Prompt，适用 gpt-4o、o3-mini、gemini-2.5-pro
- V8（V7 + Few-Shot）：仅 gpt-4o-mini 等小模型
- V3（JSON）：mimo-v2.5-pro 专用（纯文本会导致 IndexError）
- V6（纯文本）：gemini-2.5-pro 专用（历史遗留）

**理由**：
- V7 的 <|#|> 分隔符 + <|COMPLETE|> 结尾对国产模型和 OpenAI 模型都稳定
- V8 的 Few-Shot 示例对非推理模型是额外 token 负担，仅小模型需要
- MiMo 对 JSON 格式兼容更好，纯文本反而触发解析错误

## 2026-05-01: 推理模型（o 系列）不适用于实体提取

**决策**：禁用 o1-mini、o4-mini 等推理模型用于 LightRAG 提取阶段

**理由**：
- 实体提取是格式化任务，不需要推理链
- 每轮 API 内部生成隐藏推理 token，耗时 30-90s，消耗是普通模型的 3-5 倍
- o1-mini：112s/小chunk，Cloudflare 524 超时
- o4-mini：11分钟卡在 9/15 chunk，推理链过重
- 推理模型留给需要逻辑推导的 query 环节

**注意**：o3-mini 表现不同——之前成功完成提取（173实体/264关系/6.9%孤岛率）
说明 o 系列内部也有差异，不能一概而论，但 o4-mini 确认不可用。

## 2026-05-01: gpt-5-mini 不可用于 XiaoAI + LightRAG

**决策**：不推荐在 XiaoAI 代理下使用 gpt-5-mini 做批处理提取

**理由**：
- 单个 3 句 chunk 耗时 112s，远超 gpt-4o-mini 的 3-5s
- Cloudflare 代理超时 120s，大量 chunk 触发 524 错误
- 虽 Token 价格低，但实际耗时过长，有效成本反而更高
- 即使禁用 chain-of-thought 仍保留底层推理负载

## 2026-05-06: GraphRAG 查询机制与 debug-query 需求

**决策**：将 GraphRAG / LightRAG 明确定位为“证据召回与组织层”，不是图数据库自动推理引擎；查询阶段仍然依赖 LLM 的综合能力。

**理由**：
- 图谱的核心价值是把长文本压成可复用的实体、关系、路径和证据，而不是取代查询模型。
- 查询答案的质量仍受 LLM 智力、上下文选择、问题表述和证据整合能力影响。
- 对文学分析尤其重要的，不只是最终答案，还要能审计“召回了什么证据、为什么召回、答案如何形成”。

**后续动作**：
- 增加 `debug-query` 模式，至少保存召回实体、关系、chunks、query prompt、final answer。
- 在模型对比阶段优先看可审计链路，而不是只看答案文本是否好看。

**结论**：
- GraphRAG / LightRAG 适合扩大有效上下文和沉淀结构化证据，但不是替代查询阶段 LLM 智力。

## 2026-05-07: 文档边界与研究材料分流

**决策**：重新收敛仓库文档职责，减少重复与冲突。

**约定**：
- `README.md`：使用入口
- `PROJECT.md`：AI Agent 简报
- `ARCHITECTURE.md`：当前架构说明
- `docs/decisions.md`：稳定决策记录
- `docs/plans/`：设计与实施计划
- `docs/research/`：历史实验和对比报告

**理由**：
- 避免多个文档描述同一件事但版本不一致
- 降低 agent 阅读成本
- 让历史材料和当前规范分层
