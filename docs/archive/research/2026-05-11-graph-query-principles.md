# 图谱查询原理、价值与限制

本文记录当前阶段对“图谱查询到底在做什么、为什么有价值、又为什么不能神化”的共识。重点不是宣传图谱，而是给后续研究、调参与问题设计一个稳定参照。

## 一句话结论

当前这套查询机制不是“图数据库自动推理”，也不是“模型自由发挥”。它更接近：

- 图谱负责缩小搜索空间、组织证据、暴露实体与关系；
- 正文 chunk 负责提供可追溯的文本依据；
- 查询模型负责把证据整理成自然语言分析。

因此它的本质是 **证据受约束的 GraphRAG 文学分析**。

## 工作原理

当前查询流程大致分四步：

1. 把问题转成检索关键词
   - 提取中文实体词和关系词，例如人物、门派、地点、武功、物件、情感、因果、敌对、伪装。
   - 这一步决定后续检索能否命中正确的图谱区域。

2. 从图谱中召回实体与关系
   - 先从实体向量库、关系向量库和图结构里找候选节点与边。
   - 再按预算截断，避免长篇大图把上下文全部吃掉。

3. 从原文 chunk 中补正文证据
   - 根据命中的实体和关系，回溯相关文本块。
   - 最终给查询模型的不只是图节点和关系，也包括少量正文证据。

4. 由查询模型组织答案
   - 模型不会从零开始想，而是基于检索出来的实体、关系和 chunk 组织回答。
   - 因此最终答案既有图谱约束，也有模型的综合与写作成分。

## 为什么图谱有价值

### 1. 减少自由发挥

如果直接把问题交给模型，它很容易凭常识、训练记忆或题面暗示来脑补。图谱查询的好处是先让模型在本地作品材料里找线索，而不是直接凭印象回答。

对金庸这种高知名度语料尤其重要，因为模型很可能“知道一些”，但不知道自己知道的是不是来自这次分析材料。

### 2. 提高可审计性

当前 query 结果可以保留：

- 命中的实体
- 命中的关系
- 命中的正文 chunk
- query model / index model
- token 用量
- fallback 标记

这意味着我们不只看“答案像不像对”，还可以看“它凭什么这么答”。

### 3. 让长篇材料变得可检索

对几十万到百万字符的长篇作品，直接全文问答很容易漂。图谱把文本先压成实体、关系、路径和证据索引，能让后续问题更稳定地落在相关区域。

### 4. 支撑复杂但可分解的问题

图谱最适合的问题，不是“某人是谁”，而是：

- 某条人物关系如何演化
- 某个物件如何贯穿主线
- 某个组织如何影响人物选择
- 某个角色如何在多个阵营之间移动

这些问题如果只靠词频或全文搜索，材料比较散；图谱能先把关系骨架搭出来。

### 5. 为跨作品研究准备底座

单书图谱的意义，不只在本书问答，还在于以后能做：

- 跨作品共享人物/门派/地点/武功检索
- 母题对照
- 组织功能比较
- 角色命运结构比较

这类问题对“结构化可复用材料”有强依赖，图谱比一次性全文问答更适合积累。

## 当前的主要限制

### 1. 它不是纯证据系统

虽然 query 有实体、关系和 chunk 约束，但最后答案仍然是 LLM 写出来的。

所以要区分两层：

- 证据层：召回了什么
- 组织层：模型如何解释这些证据

图谱能减少幻觉，但不能彻底消灭模型的综合偏差。

### 2. 抽象问题太容易检索失败

当前最容易失败的，不是“难题”，而是“抽象但边界不清的题”。

例如：

- “最关键的一条权力反转链是什么？”
- “阵营重组意味着什么？”
- “最重要的深层动机是什么？”

这类题同时要求系统决定：

- 什么最关键
- 哪些人物应入选
- 哪些事件该压成主链
- 什么叫权力反转或阵营重组

对当前检索层来说，抽象负担太重，容易导致召回分散，最终模型直接说信息不足。

### 3. 长篇图谱里复合关系边太多

当前长篇结果常见问题是“一条边塞进太多语义”，例如同一条边同时包含：

- 情感
- 师徒
- 影响
- 敌对
- 归属

这类边对人类阅读摘要有帮助，但对后续做关系归一、路径分析、跨作品对齐并不理想。

### 4. 别名与身份分裂仍然明显

例如同一人物可能同时以：

- 本名
- 绰号
- 身份称呼
- 他人称呼

出现在图谱里。  
如果后处理没跟上，query 结果就会被切碎。

### 5. 大图可视化不是主分析手段

长篇作品的完整 `graph.html` 很快会超过直接浏览的舒适上限。真实可用的人工检查手段，仍然是：

- 子图
- 主题视图
- query 结果
- audit / report

而不是盯着整图看。

## 什么样的问题更适合现在这套系统

### 适合

- 明确人物 + 明确关系链
- 明确组织 + 明确影响对象
- 明确阶段/节点 + 明确输出格式
- 明确物件/地点 + 明确叙事功能

例如：

- 岳不群如何从“君子剑”暴露真实权力意图？请按早期、中期、后期说明。
- 令狐冲与任盈盈的关系，如何改变他在华山、恒山、日月神教之间的位置？

### 不适合

- 没有明确实体锚点
- 要求系统先定义抽象概念
- 要求从全书自动判断“最关键的一条”
- 想一步得到接近论文结论的总括判断

## 当前最合理的定位

现阶段更准确的说法是：

这不是一个已经成熟的“文学知识引擎”，而是一个 **证据受约束、可审计、可迭代的文学分析系统原型**。

它已经能证明三件事：

1. 回答不必完全靠模型自由发挥。
2. 长篇作品可以通过图谱与 chunk 检索获得较稳定的材料组织。
3. 中高阶问题可以回答，但问题设计必须顺着图谱可检索的边界来写。

## 后续优化方向

1. 改善实体别名归并。
2. 拆解复合关系边，减少“大包边”。
3. 为长篇建立更稳定的高级 query 模板。
4. 对 query 结果保留更多显式证据摘要，而不只保留原始 debug 字段。
5. 在跨作品层继续强化“图谱负责找线索，模型负责组织答案”的工作分工。
