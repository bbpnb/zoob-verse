# Index 模型试错经验

本文记录 2026-05-10 前后关于金庸作品 index 模型、provider 路由和长篇执行的经验。目标不是给模型做绝对排名，而是为后续长篇建图和跨作品研究减少重复试错。

## 当前结论

默认 index 继续保留两条主路线：

- `deepseek-v4-flash-zh-strict-bge-m3`
- `doubao-seed-1.6-bge-m3`

这两条路线在短篇和长篇样本中都表现出较好的折中：关系类型相对稳定，泛关系率可控，成本和速度可以接受。Doubao 1.6 通常更快、更省 token；DeepSeek v4 flash 的关系表达更克制，主观上更适合作为长期图谱底座。

## 近期候选模型观察

### Doubao 2.0 Lite

`doubao-seed-2-0-lite-260428` 可以跑完《越女剑》小样本，但关系类型更容易泛化。

- 节点 / 边：`147 / 172`
- 孤岛率：约 `14.97%`
- 关系退化率：约 `9.30%`
- 泛关系率：约 `15.12%`

结论：可用但不优先。它的价值更像低成本备选，而不是替换 Doubao 1.6。

### Doubao 1.5 Pro 32K

`doubao-1-5-pro-32k-250115` 可以跑完《越女剑》小样本，但泛关系率明显偏高。

- 节点 / 边：`138 / 169`
- 孤岛率：约 `15.22%`
- 泛关系率：约 `30.18%`

结论：不推荐用于日常 index。它并没有因为“Pro”而更适合结构化抽取，反而更容易把多种关系揉成泛泛的 `关联`。

### SiliconFlow DeepSeek V3.2 Pro

`Pro/deepseek-ai/DeepSeek-V3.2` 可以跑通，并且节点覆盖不低，但主观质量不如 DeepSeek v4 flash。

- 规范化后节点 / 边：`128 / 169`
- 孤岛率：约 `12.03%`
- 泛关系率：约 `12.79%`
- 《越女剑》小样本 index 耗时：约 `785.829s`

主观观察：

- 优点是覆盖更满，孤岛率更低。
- 问题是更像在写综合摘要，而不是抽取干净的图谱边。
- 例如 `范蠡 -[出没]-> 阿青` 的描述包含招揽、陪伴、保护、爱慕、怨恨、威胁等多种关系，作为人读材料可用，作为单条图谱边偏脏。
- 还出现 `勾践 -[情感]-> 越王允常` 这类类型不准的边。

结论：V3.2 Pro 不算不可用，但不适合作为长篇 index 主力。它更可能适合后续主题摘要、材料整理或二次分析，而不是第一阶段建图。

### SiliconFlow DeepSeek V4 Flash

`deepseek-ai/DeepSeek-V4-Flash` 已通过连通性 smoke test，可作为 DeepSeek 官方路由之外的备用 provider。它是否质量等同官方，还需要同一文本、同一参数、同一 prompt 的短篇完整对照。

## 长篇执行补充

### SiliconFlow DeepSeek V4 Flash 不适合当前长篇正式路线

《侠客行》长篇正式实验中，`deepseek-v4-flash-siliconflow-bge-m3` 在远端 worker 上于 `26 / 319` chunk 处失败，报错为 `Worker execution timeout after 1800s`。这不是简单的本地中断，而是 LightRAG 文档处理阶段的 LLM worker 超时。

需要区分两件事：

- LightRAG 对失败 run 的重跑，更接近“同一文档重试”，不是严格意义上的 chunk 级断点续跑。
- 因为失败前尚未产出最终图谱，所以继续用同一 provider 复跑，仍有较大概率撞上同类慢请求或 provider 侧不稳定。

基于这次实测，当前判断是：

- SiliconFlow DeepSeek V4 Flash 可保留为短篇实验或备用路线。
- 但它暂时不应承担长篇正式 index 主力。
- 至少在当前参数和 worker 资源条件下，它的长篇稳定性弱于 DeepSeek 官方路由，也弱于 Doubao 1.6 这条已验证路线。

### Doubao 1.6 在《侠客行》长篇上验证通过

失败后，将《侠客行》切换到 `doubao-seed-1.6-openrouter-bge-m3` 重跑，远端完整跑通。

- 节点 / 边：`1265 / 1785`
- 孤岛率：约 `20.00%`
- 最大连通分量：约 `76.21%`
- relation degradation：约 `11.82%`
- 总 token：约 `1023172`
- 总耗时：约 `10581s`，即 `2.94h`

这说明 Doubao 1.6 不只是短篇可用，在十万字级别长篇上也具备当前流程下的正式可用性。

### DeepSeek 官方 V4 Flash 在《笑傲江湖》长篇上验证通过

《笑傲江湖》使用 `deepseek-v4-flash-zh-strict-bge-m3` 完整跑通。

- 节点 / 边：`2646 / 4797`
- 孤岛率：约 `18.07%`
- 最大连通分量：约 `79.29%`
- relation degradation：约 `13.82%`
- 总 token：约 `4527339`
- 总耗时：约 `39304s`，即 `10.92h`

结论并不意外：更长文本会显著放大总耗时与图规模压力，但官方 DeepSeek 路由在稳定性上仍然过关。

## 长篇主观观察

目前的主观判断仍是：

- DeepSeek v4 flash 的关系表达更克制，作为图谱底座更稳。
- Doubao 1.6 的速度和 token 开销更友好，而且在《侠客行》上没有出现明显质量塌陷。
- 但到了《射雕英雄传》《神雕侠侣》这种更长文本，二者差异被进一步放大：
  - DeepSeek v4 flash 在主干人物、主干关系上通常更稳，跨作品污染更少。
  - Doubao 1.6 的 token 效率显著更高，更适合继续把 corpus 快速铺开。
  - 两条路线都还不能直接当“最终可研究图谱”，更合理的定位是第一阶段高召回底座。

但两者也暴露了共同问题：

- 长篇核心人物关系边容易变成“多语义大包边”，即一条边同时塞入情感、师徒、影响、敌对、归属等多个层次。
- 例如《侠客行》中 `谢烟客 -> 石破天`、`谢烟客 -> 小丐`，以及《笑傲江湖》中 `林平之 -> 岳灵珊`、`林平之 -> 岳不群`，都更像人物关系总述，而不是单一语义边。
- 这种写法对人读摘要有帮助，但会增加后续实体对齐、关系归一和主题分析的成本。

### 《射雕英雄传》与《神雕侠侣》补充结论

这一轮长篇完成后，可以更明确地给出一个现实判断：

- 《射雕英雄传》使用 `deepseek-v4-flash-zh-strict-bge-m3`
  - 节点 / 边：`3329 / 5378`
  - LLM token：`4699363`
  - embedding token：`1267727`
- 《神雕侠侣》使用 `doubao-seed-1.6-openrouter-bge-m3`
  - 节点 / 边：`3386 / 4729`
  - LLM token：`239501`
  - embedding token：`1320287`

两部作品文本规模接近，但 LLM token 差距极大。这至少说明：

1. DeepSeek 默认路线在长篇上仍有明显的 completion 膨胀问题。
2. Doubao 1.6 在长篇 index 上的单位 token 产出更高。
3. 仅从宏观指标看，Doubao 1.6 并未出现“便宜但完全不可用”的质量塌陷。

但人工抽查也暴露出新的边界：

- DeepSeek 路线：
  - 主干人物实体和主干关系更稳。
  - 主要问题是描述过长、关系标签偏泛、单边承载过多语义。
- Doubao 路线：
  - 成本显著更低，适合继续铺完整体 corpus。
  - 但更容易出现跨作品污染或模型先验混入，例如《神雕侠侣》图中出现 `令狐冲`、`岳灵珊` 这类明显不属于该书的实体。
  - 关系标签漂移也更明显，如把亲属/情感/敌对关系打成 `传授`、`师徒` 等。

因此，对当前长篇图谱的合理定位应是：

- 它们已经足够支撑下一阶段的后处理、实体对齐、主题裁剪和证据化 query 设计。
- 但还不应被直接视为“最终严谨图谱”。
- 更实际的路线是先把剩余作品尽量跑完，再统一做后处理，而不是现在就对单本图谱做过细修补。

因此，对长篇 index 的判断不能只看“跑通了没有”，还要继续看：

1. 核心人物边是否可拆。
2. 同一人物是否存在大量别名分裂，例如 `小丐 / 狗杂种 / 石破天`。
3. 关系类型是否过度复合。
4. 大图是否已经超过直接可视化的可用上限。

## 经验教训

### 强模型不一定更适合 index

index 阶段更像“高约束结构化抽取”，不是开放式文学分析。模型越会综合、解释、铺陈，有时越容易把多种事实压进一条长描述，导致关系类型变脏。

对 index 来说，优先级大致是：

1. 严格遵守实体/关系 schema。
2. 边类型稳定，少用泛关系。
3. 描述像证据摘要，而不是长篇分析。
4. 召回足够主要实体和核心关系。
5. 成本和速度可接受。

节点更多不一定更好。低孤岛率也不必然更好，因为它可能来自弱连接或泛连接。

### 关系质量比覆盖数量更重要

后续跨作品实体对齐、主题视图、路径分析和证据化查询，都依赖边类型和边描述。如果 index 阶段大量产生 `关联` 或混合关系，后处理会变得更难。

因此模型对比不能只看：

- 节点数
- 边数
- 孤岛率

还必须看：

- `generic_relation_rate`
- `relation_degradation_rate`
- compound relation type 比例
- 关键人物关系的主观可读性
- 是否把多个语义关系塞进一条边

### Provider 速度需要同条件验证

SiliconFlow 上调用 DeepSeek 模型主观上可能更快，但目前不能直接断言。原因是不同实验之间常常同时变化了：

- 模型本身是否相同。
- provider 路由和排队情况。
- embedding provider 是否相同。
- 是否命中 prompt cache。
- 是否本地或远端执行。
- 文本是否清洗过。
- 任务是否包含 query、audit、visualize、report。

目前可以说：

- SiliconFlow 的 DeepSeek 路由可用。
- 体感速度可能不错，值得保留为备用并行路线。
- 但它在《侠客行》长篇正式任务上曾出现 1800s worker timeout，因此当前不能把“体感更快”直接等同于“更适合长篇正式运行”。
- 要判断“是否比官方 DeepSeek 快”，需要用同一作品、同一清洗文本、同一 prompt、同一 embedding、同一并发参数跑完整 A/B。

建议只在有实际调度需求时验证，不为速度错觉单独消耗太多 token。

## 后续建议

1. 在 corpus 仍未跑完前，长篇正式 index 继续优先使用 Doubao 1.6 或经过验证的 DeepSeek 路线。
2. 如果核心目标是“先把金庸宇宙尽快铺完”，当前更偏向 Doubao 1.6 这条高性价比路线。
3. 如果要为某部作品建立高质量样板图谱，可保留 DeepSeek 路线做少量精品样本。
4. 新模型先跑《越女剑》这类短篇完整 index，达不到主路线质量就不跑长篇。
5. 对候选模型的判断以“是否减少后处理负担”为核心，而不是只看是否能生成更多节点。
6. 查询阶段可以使用更强或更会写的模型，但 index 阶段应继续偏向稳定、克制、格式遵守好的模型。
