# 金庸图谱项目复盘

这份文档不是新的施工计划，而是把前面零散的 research、plans 和对话经验压缩成一份可读总结。它回答四个问题：我们为什么做，实际怎么做，踩了什么坑，现在能用来做什么。

## 1. 初衷

项目的初衷不是做一个“让 AI 更会聊金庸”的玩具，而是尝试构建一套可复用的数据资产：把金庸作品中的人物、组织、地点、武功、物件和关系抽取成图谱，再用图谱支持更有证据边界的文学分析。

普通 AI 对话的问题是，它可以讲得很顺，但证据来源常常不清楚。我们希望回答问题时先检索图谱，再组织分析。这样至少能做到：

- 重要判断有实体和关系可查；
- 跨书比较不是凭印象，而是有全局索引；
- 明确区分图谱直接支持、基于证据的推断、证据不足处；
- 后续可以接到其他应用里，而不是只留在一次聊天上下文中。

## 2. 实际过程

项目大致走过五个阶段。

第一阶段是短篇和小样本试验。我们先用《越女剑》《连城诀》前几章等样本验证 LightRAG 建图流程、模型可用性、实体和关系质量。这个阶段的目标是确认方法能跑通，而不是追求最终数据。

第二阶段是长篇建图。我们陆续跑完金庸 15 部作品，期间尝试了 DeepSeek V4 Flash、Doubao 1.6、Doubao 2.0 Lite、Doubao 1.5 Pro、SiliconFlow 上的 DeepSeek 模型等。后来基本确认 DeepSeek V4 Flash 和 Doubao 1.6 是相对可用的主力选择，其他模型要么质量不足，要么成本/稳定性不合适。

第三阶段是并行和远端流程。为了处理长篇成本和时间，我们尝试在远端并行跑不同作品，并用不同 provider 分散限流风险。这个方向可行，但也暴露出 provider 稳定性、限速、任务中断、API key 安全和账单监控问题。

第四阶段是成本控制。长篇图谱抽取会产生大量 completion token，尤其是关系描述过长时，成本会迅速失控。后来验证 no-thinking 模式能明显改善 token 使用效率，同时对图谱质量的影响可接受。这个经验对后续其他语料非常重要。

第五阶段是后处理和收敛。原始图谱有价值，但也有噪声：称谓、泛称、跨作品污染、同名误合并、候选层混乱等。我们做了 scorecard、噪声候选、全局人物层、称谓过滤、跨书候选分类等后处理。后续又发现文档和中间文件太多，使用体验开始变差，于是把成果收敛成 `artifacts/jinyong-v1`。

## 3. 主要成果

当前最重要的成果不是某一篇 research 文档，而是一个可使用的数据包：

```text
artifacts/jinyong-v1/
```

它包含：

- 15 部作品的主图谱；
- 每部作品的 `graph.json` 和 `report.json`；
- 全局人物索引 `global/people.json`；
- 跨书人物候选 `global/crosswork_people.json`；
- 噪声摘要 `global/noise_summary.json`；
- 查询模板和可读样例。

这套数据包的价值在于：它把 `runs/` 中复杂的实验结果，整理成别人可以直接读取的稳定路径。其他 AI agent 或下游应用不必理解模型试验、主 run 选择和后处理历史，也能开始使用。

## 4. “分析层”和“使用层”

现在项目应该明确分成两层。

使用层是 `artifacts/jinyong-v1`。这是默认入口。文学查询、演示、下游应用和外部 agent 都应该先看它。

分析层是 `runs/`、`docs/research/`、`docs/plans/`、`WORKFLOWS.md` 和 `src/modules/jinyong/postprocess.py`。它们用于重跑、维护、复盘和学习，不应该让普通使用者天天打开。

“降级 research/plans”不是删除，也不是否定价值。它只是把这些文件从“使用前必须读的材料”降为“需要追溯时再看的档案”。这能避免每次问一个文学问题，都被迫解释施工过程。

## 5. 当前能用来做什么

当前成果适合做四类事情。

第一类是单书分析。例如分析《笑傲江湖》中令狐冲与岳不群的师徒破裂，或《鹿鼎记》中韦小宝如何连接皇权、天地会、吴三桂和神龙教。

第二类是跨书比较。例如比较郭靖、杨过、张无忌的跨书出现方式，或比较少林、武当、丐帮在不同作品中的组织功能。

第三类是主题研究。例如比较《碧血剑》《书剑恩仇录》《鹿鼎记》的反清主题，或梳理由秘籍、兵器、宝物推动冲突的模式。

第四类是数据产品原型。例如做一个金庸人物关系查询工具、跨书人物索引、主题探索界面，或给其他 AI agent 提供检索上下文。

## 6. 不能做什么

当前图谱不能直接当绝对可靠的百科。它来自模型抽取，不是人工精校知识库。

它也不适合回答完全没有证据边界的问题，比如“金庸小说的终极哲学是什么”。这类问题可以讨论，但必须先拆成具体人物、关系、作品和证据，否则会回到普通 AI 自由发挥。

它也不能替代原文细读。图谱擅长找线索、组织关系和暴露结构，但文学判断仍需要回到文本细节。

## 7. 关键经验

第一，图谱不是目的，图谱支持的问题才是目的。如果提问太空泛，图谱也会变成复杂装饰。

第二，长篇建图成本必须提前控制。模型选择、thinking 开关、completion 长度、provider 稳定性和账单监控都不是小问题。

第三，多 run 和多模型实验有技术价值，但不能无限保留为使用复杂度。实验结果应被吸收到一套干净的成果包里。

第四，后处理不能只追求复杂规则。好的后处理应该减少使用者负担，而不是制造更多必须理解的中间层。

第五，外部 agent 需要明确入口。最有效的提示不是“读完整个项目”，而是“基于 `artifacts/jinyong-v1`，按证据边界回答问题”。

## 8. 目前仍然不完善的地方

关系类型还比较粗。有些边虽然描述丰富，但 `type` 可能只是“关联”“影响”“传授”，不够适合统计分析。

组织层、武功层、物件层还没有像人物层那样整理。少林、武当、丐帮、明教、天地会，或者九阴真经、独孤九剑、倚天剑、屠龙刀，都值得形成更清晰的专题索引。

跨书人物候选仍需要人工抽样复核。连续作品共享、真实引用和模型污染之间，有些边界仍不清楚。

可读分析样例还不够多。要证明这套数据真的好用，需要继续做面向普通读者的问题和答案，而不是只展示工程指标。

## 9. 建议的下一步

短期最值得做的是扩展 `artifacts/jinyong-v1/examples/sample_answers.md`，做出 5 到 10 个真正可读的分析样例。每个样例都用同一结构：一句话结论、关键证据、图谱直接支持、基于证据的推断、不确定处。

第二步是做关系归一的小实验。先不要全量重构，可以抽样看常见关系类型，把“关联”中明显可分的夫妻、师徒、敌对、隶属、使用、传承等关系整理出来。

第三步是做组织层。人物层已经证明后处理有价值，下一类最值得整理的是组织，因为门派、帮会、朝廷、军队和秘密组织对金庸分析很关键。

第四步才是考虑产品化。产品不应该暴露 `runs/` 和 research 文档，而应该只暴露成果包和查询接口。

## 10. 给其他 AI agent 的最短说明

如果要让其他 AI 使用当前成果，可以直接给它这段话：

```text
请基于 artifacts/jinyong-v1 金庸图谱数据包回答问题。先读 README.md 和 manifest.json，再按需要读取 works/<作品>/graph.json、global/people.json、global/crosswork_people.json。

回答要面向普通读者，不要解释工程过程。请明确区分：图谱直接支持的证据、基于证据的推断、证据不足或需要原文复核的地方。
```

这就是当前项目从复杂过程收敛出来的核心使用方式。
