# LightRAG 原理与适用场景

本文档记录 LightRAG 的工作原理、查询机制，以及除文学分析外的适用场景。

---

## 一、LightRAG 是什么

LightRAG（Light Retrieval-Augmented Generation）是一个**基于知识图谱的增强检索生成框架**。与传统 RAG 只做向量相似度搜索不同，LightRAG **同时维护知识图谱 + 向量索引**，查询时利用图谱的结构信息做更精确的召回。

核心差异：

| | 传统 RAG | LightRAG |
|---|---|---|
| 索引方式 | 仅向量 | 图谱 + 向量双索引 |
| 检索方式 | 文本相似度 | 实体中心扩展 + 关系模式 + 文本向量 |
| 间接关系 | 依赖 chunk 重叠 | 通过图边路径直接发现 |
| 预算控制 | chunk 数量 | top_k + chunk_top_k + token budget |

---

## 二、索引阶段（Index）

索引流程：`ainsert(text)` → chunking → 实体抽取 → 关系抽取 → 图合并 → 双索引

### 2.1 文本分块（Chunking）

将输入文本按固定大小切分为 chunks。LightRAG 内部策略约 1,160 字符/chunk。

> 以连城诀前五章为例：98,609 字符 → **85 个 chunks**

每个 chunk 做 embedding 存入 `vdb_chunks.json`。

### 2.2 实体抽取（Entity Extraction）

对每个 chunk，调用 LLM 按 schema 提取实体：

```
entity｜>狄云｜>人物｜>连城诀主角，被诬陷入狱
entity｜>戚长发｜>人物｜>狄云的师父，外表老实实则阴险
entity｜>神照功｜>武功｜>丁典传授的绝顶内功
```

> 连城诀前五章共抽到 **434 个实体**，类型涵盖人物、组织、地点、武功、兵器、物件、事件、概念、生物。

### 2.3 关系抽取（Relationship Extraction）

对每对实体抽取关系，N-ary 关系需分解为二元对：

```
relation｜>狄云｜>丁典｜>师徒｜>丁典传授狄云神照功
relation｜>戚长发｜>万震山｜>敌对｜>同为梅念笙弟子，因争夺连城剑谱产生矛盾
relation｜>丁典｜>连城诀｜>使用｜>丁典掌握连城诀中的宝藏秘密
```

> 连城诀前五章共抽到 **516 条关系**。

### 2.4 图合并（Graph Merging）

将 85 个 chunk 的抽取结果合并到**一个全局图**中。同名实体合并（如"狄云"在多个 chunk 中出现，合并为一个节点），关系叠加。

### 2.5 双索引构建

- **知识图谱索引**：`graph_chunk_entity_relation.graphml`，包含节点和边的完整拓扑结构
- **向量索引**：
  - 实体向量：每个实体的 description → embedding → `vdb_entities.json`
  - 关系向量：每条关系的 description → embedding → `vdb_relationships.json`
  - 文本向量：每个 chunk 的内容 → embedding → `vdb_chunks.json`

### 2.6 索引阶段实际数字（连城诀前五章）

| 指标 | 值 |
|---|---|
| 输入文本 | 98,609 字符 |
| Chunks | 85 |
| LLM 调用次数 | 85 次 |
| 抽取实体 | 434 |
| 抽取关系 | 516 |
| Embedding 调用 | 434 + 516 + 85 = 1,035 次 |
| LLM tokens | 253,080 |
| 索引耗时 | ~60 分钟 |

## 三、查询阶段（Query）

查询流程：关键词提取 → 图谱检索 → 向量检索 → 重组上下文 → LLM 生成

### 3.1 关键词提取

用 LLM 从问题中抽取两类关键词：

```json
{
  "high_level_keywords": ["人物动机", "情感", "利益", "行为原因"],
  "low_level_keywords": ["狄云", "丁典", "凌霜华"]
}
```

- `high_level`：主题、关系类型、分析角度（用于关系检索）
- `low_level`：具体实体名（用于实体检索）

### 3.2 查询模式

LightRAG 支持 **6 种查询模式**：

| 模式 | 检索方式 | 适用场景 |
|---|---|---|
| **local** | 实体中心扩展 + 关系向量 + chunk 向量 | 针对具体人物/实体的问题 |
| **global** | 全图谱关系模式搜索 + chunk 向量 | 宏观趋势/整体结构问题 |
| **hybrid** | local + global 合并 | 需要多视角的问题 |
| **naive** | 纯向量 chunk 搜索（不用图） | 简单事实查询 |
| **mix** | local + global + naive + rerank | 最全面，官方推荐 |
| **bypass** | 不调用图/向量，直接问 LLM | 基线对比 |

### 3.3 Local Mode 详解

以查询"丁典和凌霜华的故事是什么？"（local 模式）为例：

**Step 1：实体检索**
- 用 `low_level` 关键词 ["丁典", "凌霜华"] 在实体向量库中检索
- 找到最相关的实体："丁典"、"凌霜华"
- 从图谱中展开这些实体的 **1-hop 邻居**（直接相连的节点）
  - 丁典的邻居：凌霜华、狄云、凌退思、连城诀、神照功…
  - 凌霜华的邻居：丁典、凌退思、金波旬花、绿色菊花…

**Step 2：关系检索**
- 用 `high_level` 关键词 ["爱情故事", "情感", "悲剧"] 在关系向量库中检索
- 按 top_k=6 返回最相关的关系（如丁典→凌霜华 的"情感"关系、丁典→凌退思 的"敌对"关系等）

**Step 3：向量检索（chunk 侧）**
- 用关键词做向量相似度搜索，召回最相关的原文 chunk（chunk_top_k=4）
- 返回 4 条包含丁典凌霜华故事的关键原文段落

**Step 4：重组上下文**
- 将召回的实体描述、关系描述、原文 chunk 组装成 LLM prompt
- 受 token 预算控制：max_total_tokens=10000, max_entity_tokens=2500, max_relation_tokens=2500

**Step 5：LLM 生成答案**
- LLM 基于上下文（而非凭空记忆）生成回答

### 3.4 预算控制参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| `top_k` | 60 | 召回的实体/关系数量（取决于查询模式） |
| `chunk_top_k` | 20 | 召回的原文 chunk 数量 |
| `max_total_tokens` | 30000 | 总上下文 token 预算 |
| `max_entity_tokens` | 6000 | 实体信息 token 上限 |
| `max_relation_tokens` | 8000 | 关系信息 token 上限 |
| `enable_rerank` | true | 是否对 chunk 做 rerank |

### 3.5 查询阶段实际数字（连城诀前五章）

| 指标 | 值 |
|---|---|
| 查询数 | 8 个 |
| 查询 tokens | 58,851 |
| 高质量回答 | 7/8 |
| 召回不足 | 1/8（凌退思的动机 — local 模式证据不够） |
| 平均每题耗时 | ~15 秒 |

## 四、核心优势

### 4.1 间接关系发现

传统 RAG 只能找到与查询向量相似的内容。LightRAG 通过图谱路径可以发现间接关系：

> 问："狄云和宝象有什么关系？"
> 直接文本搜索：无直接关联。
> 图谱路径：狄云 → 丁典 → 越狱 → 宝象追杀 → 狄云抵抗。通过 3-hop 路径建立关联。

### 4.2 跨 chunk 上下文聚合

> 丁典的故事分散在 10+ 个 chunk 里。向量搜索只能召回最相似的几个，但图谱的丁典节点通过邻居扩展一次性聚合了所有相关 chunk。

### 4.3 预算可控的查询

> 长文本 98K 字符，全文塞给 LLM 会超出上下文。LightRAG 通过 top_k、chunk_top_k、token budget 控制召回量在 10K tokens 以内，同时保证信息密度。

### 4.4 可审计性

> debug 查询返回完整的召回实体、关系、chunks，可以追踪"为什么召回这些、答案基于哪些证据"。

## 五、适用场景

LightRAG 的核心能力是：**多跳推理 + 结构感知 + 预算可控的检索 + 可审计的证据链**。这些能力不仅适用于文学分析，还适用于以下场景：

### 5.1 法律文档分析

| 能力 | 应用场景 |
|---|---|
| 实体/关系抽取 | 法律条文、案例、当事人、条款、判决 |
| 多跳推理 | 某条款如何影响特定当事人的权利 |
| 跨文档关联 | 不同法规之间的引用和冲突 |

**示例**：输入一套公司法 + 相关判例，查询"某公司创始人如何通过股权结构变更失去控制权？"——图谱可以通过"创始人 → 持股 → 公司 → 变更 → 董事会 → 决议 → 控制权转移"的多跳路径发现完整链条。

### 5.2 生物医学知识管理

| 能力 | 应用场景 |
|---|---|
| 知识图谱 | 疾病、症状、药物、基因、通路、文献 |
| 多跳推理 | 某种药物通过哪些通路影响哪些基因表达 |
| 间接发现 | 发现药物重定位的潜在路径 |

**示例**：输入一批医学文献，查询"药物 A 的副作用是否可能与靶点 B 的调控通路有关？"——图谱可以通过"药物 A → 副作用 → 靶点 B → 调控通路 → 疾病 C"发现间接关联。

### 5.3 传记/人物研究

| 能力 | 应用场景 |
|---|---|
| 人物/事件抽取 | 传记中的人物、事件、地点、组织 |
| 时间线重建 | 人物一生中关键事件的因果链 |
| 跨人物分析 | 多个人物之间的关系网络 |

**示例**：输入一个人物的多篇传记和日记，查询"某人在某个历史事件中的角色和动机是什么？"——图谱可以聚合分散在多份材料中的相关人物和事件。

### 5.4 软件架构与依赖分析

| 能力 | 应用场景 |
|---|---|
| 实体抽取 | 模块、函数、类、接口、依赖 |
| 关系抽取 | 调用关系、继承、依赖、数据流 |
| 影响分析 | 修改某个模块会影响哪些下游组件 |

**示例**：对大型代码库建索引后查询"修改用户认证模块会影响哪些功能？"——图谱可以通过调用链和依赖图追踪完整的 impact 路径。

### 5.5 安全分析与威胁建模

| 能力 | 应用场景 |
|---|---|
| 实体抽取 | 系统组件、攻击面、漏洞、缓解措施 |
| 关系抽取 | 攻击路径、数据流、信任边界 |
| 攻击链发现 | 从入口点到核心资产的完整攻击路径 |

**示例**：输入系统架构文档，查询"攻击者如何从公网访问到数据库？"——图谱可以构建"公网入口 → 防火墙 → 内部网络 → 数据库 → 敏感数据"的攻击路径。

### 5.6 供应链与溯源

| 能力 | 应用场景 |
|---|---|
| 实体抽取 | 供应商、原材料、产品、物流节点 |
| 关系抽取 | 供货关系、加工关系、运输关系 |
| 溯源追踪 | 从成品追溯到原材料供应商 |

**示例**：输入供应链数据，查询"某原材料的缺陷会影响哪些最终产品？"——图谱可以通过"原材料 → 半成品 A → 产品 X"和"原材料 → 半成品 B → 产品 Y"两条路径发现完整影响范围。

### 5.7 历史研究与事件分析

| 能力 | 应用场景 |
|---|---|
| 实体抽取 | 人物、事件、地点、组织、文献 |
| 关系抽取 | 因果关系、时间顺序、参与关系 |
| 事件链重建 | 一系列历史事件的因果链 |

**示例**：输入一个历史时期的文献，查询"某场战争的起因和关键转折点是什么？"——图谱可以通过"经济矛盾 → 外交危机 → 军事冲突 → 关键战役 → 和平谈判"的路径重建事件链。

### 5.8 教育课程与知识管理

| 能力 | 应用场景 |
|---|---|
| 实体抽取 | 概念、术语、知识点、先修知识 |
| 关系抽取 | 先修关系、包含关系、关联关系 |
| 学习路径 | 从基础概念到高级主题的依赖路径 |

**示例**：输入一门课程的教材，查询"学习微积分需要哪些前置知识？"——图谱可以通过"微积分 → 依赖 → 极限 → 依赖 → 函数 → 依赖 → 代数"重建学习路径。

## 六、通用适用条件

如果一个场景满足以下条件中的多个，LightRAG 就有潜在价值：

1. **复杂关系结构**：存在大量实体和它们之间的多类型关系
2. **多跳推理需求**：答案不是简单的事实查找，需要经过 2-3 跳的推理路径
3. **长文本/多文档**：全文超出上下文窗口，或需要跨文档检索
4. **预算敏感**：需要在信息量和 token 成本之间做精细控制
5. **可审计性**：需要知道答案的证据来源和推理路径
6. **反复查询**：一次建索引，多次复用查询

---

## 七、不适合的场景

以下场景不需要 LightRAG，传统方法更合适：

- 只需对短文做摘要 → 直接全文问答
- 简单事实查找（"某人的生日"） → 传统 RAG 或数据库
- 关系结构单一（线性文本，几乎没有交叉引用） → 纯向量搜索即可
- 目标是一次性回答，没有后续复用 → index 成本不划算
- 需要精确数值计算 → 这是工具调用/代码执行的任务，不是检索

## 八、Zoob-verse 中的实践

当前项目使用 LightRAG 对金庸武侠小说做知识图谱索引和分析：

- **模型**：deepseek-v4-flash / doubao-seed-1.6（LLM）+ BGE-M3（embedding）
- **Prompt**：V10 全中文图谱抽取（严格 schema）
- **已索引作品**：越女剑、鸳鸯刀、连城诀、书剑恩仇录、碧血剑、雪山飞狐、飞狐外传、白马啸西风、笑傲江湖
- **核心流程**：索引 → 归一化 → 审计 → 查询评估 → 报告

完整模型对比数据见 [docs/research/2026-05-10-index-model-lessons.md](2026-05-10-index-model-lessons.md)。
